# Скилл: Харвестер (Анализ и Улучшение)

## Назначение
Анализ ошибок, проблем и найденных Issues после завершённого цикла теста. Выявление повторяющихся паттернов, обновление правил и PO для предотвращения ошибок в будущем.

## Когда использовать
После того как Ревью и Правки (04) подтвердили, что тест проходит и качество на уровне. Запускается в конце каждого цикла написания теста (один тест = один харвест).

## Порядок выполнения

### Шаг 1: Сбор сигналов из цикла
Собрать информацию из только что завершённого цикла:
- Какие ошибки возникли при написании кода? (категории из test-reliability.md / test-antipatterns.md)
- Какие проблемы нашёл Ревью? (какие аннотации были добавлены)
- Сколько раз пришлось перезапускать тест до PASS?
- Что пришлось править в PO после ревью?
- Какие ассерты/локаторы вызывали больше всего флаков?

### Шаг 2: Анализ повторяющихся паттернов
Проверить, были ли похожие проблемы в предыдущих тестах:
- Те же пункты чек-листов срабатывают чаще всего?
- Какие PO методы не хватало и пришлось создавать?
- Какие страницы/элементы требуют особых подходов?

### Шаг 3: Обновления (preview → approve)
На основе анализа предложить и применить улучшения:

**3a: Page Objects**
- Добавить недостающие универсальные методы в конкретный PO или BasePage
- Добавить robust локаторы для проблемных элементов (цепочка `.filter().or()`)

**3b: Config / Constants**
- Добавить новые константы в `config.ts` (селекторы, таймауты, test data)
- Добавить `DATA_TEST` атрибуты если нужны стабильные хуки

**3c: Чек-листы ревью**
- Обновить `test-reliability.md` / `test-antipatterns.md` / `test-pom-review.md` если найден новый паттерн
- Добавить примеры из реального кода проекта

**3d: AGENTS.md**
- Если найден новый анти-паттерн или best practice — предложить добавление в AGENTS.md

### Шаг 4: Регресс
Запустить полный регресс для роли (или all) — убедиться, что улучшения не сломали существующие тесты:
```bash
npm run test:owner    # или coach/parent/athlete/all
```

### Шаг 5: Финальный отчёт
```
## Харвестер: [Дата] — [Тест/Функционал]

### Статистика цикла:
- Тестов написано: [N]
- Запусков выполнено: [N]
- Ошибок исправлено: [N]
- Повторяющихся паттернов: [N]

### Топ проблем чек-листов:
1. [Пункт чек-листа] — [сколько раз встретился]
2. ...

### Внесённые улучшения:
- PO: [какой метод/локатор добавлен в какой файл]
- Config: [какая константа добавлена]
- Skills: [какой чек-лист обновлён]
- AGENTS.md: [какое правило добавлено/изменено]

### Готово:
Все тесты проходят, качество проверено, уроки зафиксированы.
```

## Правила
- ВСЕГДА анализировать ошибки, даже если тест прошёл с первого раза
- ВСЕГДА искать повторяющиеся паттерны — это ключ к предотвращению ошибок
- ВСЕГДА фиксировать lessons-learned для будущего
- НЕ переусердствовать — если цикл был простым и без ошибок, отметить это
- Предлагать улучшения, а не просто констатировать факты
- Сохранять баланс: не оптимизировать то, что и так работает хорошо
- **ПЕРЕД обновлением скиллов/памяти:** проверить существующие записи — новые не должны противоречить им
- **НЕ раздувать объёмы скиллов и памяти без необходимости** — они должны оставаться полностью читаемыми агентами
- Если улучшение — подпункт существующего раздела (а не новый раздел) — предпочесть это
- Дублирование правил допустимо и иногда полезно для надёжности (агент видит правило в контексте, не ищет ссылку)
- Но избегать дублирования если правило уже описано достаточно подробно в целевом файле
