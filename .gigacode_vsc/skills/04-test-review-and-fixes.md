# Скилл: Ревью и Правки

## Назначение
Проведение глубокого ревью написанного теста, выявление скрытых проблем, улучшение читаемости и надёжности, внесение правок и подтверждение прохождения тестов.

## Когда использовать
После того как Писатель Тестового Кода получил проходящий тест. Здесь не боремся за то, чтобы тест прошёл, а ищем возможности улучшить качество.

## Холодное ревью — критическое правило

**Ревью должно быть «холодным» — как если бы код написал другой разработчик.**

### Что это значит:
- ✅ Смотрим **только на финальный код** (текущее состояние файлов)
- ✅ Оцениваем так, будто код написан с нуля неизвестным автором
- ✅ Не подтягиваем историю правок, черновики, отброшенные варианты
- ✅ Не анализируем, что было до и почему выбрали такой подход

### Что ЗАПРЕЩЕНО:
- ❌ Не смотреть на diff/историю изменений
- ❌ Не упоминать отброшенные варианты
- ❌ Не анализировать ошибки, которые были исправлены в предыдущих шагах
- ❌ Не ссылаться на контекст предыдущих скиллов при оценке кода
- ❌ Не оценивать "почему так сделано" — только "что написано сейчас"

### Почему это важно:
Ревью — это проверка **текущего состояния** кода. Если в тесте есть проблема — она есть независимо от того, сколько раз его правили.

## Checklist — стартовый чекпоинт

Перед началом ревью пройти по каждому пункту. Каждый пункт — ✅ или ❌.

### A. Архитектура и POM
| # | Проверка |
|---|---------|
| A1 | В тестах нет прямого `page.getByRole` / `page.locator` / `page.getByText` — только методы PO |
| A2 | Локаторы объявлены в конструкторе PO один раз, не в методах |
| A3 | Методы PO: actions не возвращают boolean, проверки (`expect`) только в тестах |
| A4 | Нет дублирования локаторов между PO |
| A5 | Локаторы используют `getByRole` / `getByPlaceholder` — не CSS/XPath |
| A6 | Robust row search: `getByRole('row', { name: regex }).or(...)` |

### B. Web-first ассерты
| # | Проверка |
|---|---------|
| B1 | Все ассерты через `await expect(...)` — авто-ретрай, не одна попытка |
| B2 | Нет `expect(await locator.count()).toBe()` — использовать `toHaveCount` |
| B3 | Нет `expect(await locator.textContent())` — использовать `toHaveText` |

### C. Стабильность
| # | Проверка |
|---|---------|
| C1 | Нет `waitForTimeout` / `sleep` |
| C2 | Нет `try/catch` для глушения ошибок |
| C3 | Нет `.catch(() => {})` в ассертах |
| C4 | Нет хрупких селекторов (`nth-child`, абсолютные XPath) |
| C5 | Таймауты только из `config.ts` (`TIMEOUTS.*`), не хардкод |

### D. Тестовые данные
| # | Проверка |
|---|---------|
| D1 | Уникальные имена через `Date.now()` или `Math.random()` — не хардкод |
| D2 | Нет прод-данных в тестах |
| D3 | Cleanup в `afterEach` удаляет ВСЕ созданные данные (цикл, не одно значение) |

### E. Авторизация
| # | Проверка |
|---|---------|
| E1 | Используется `loginAs(role)` fixture |
| E2 | Для logout/redirect/signup тестов — UI-логин без storageState кэша |

### F. Поддерживаемость
| # | Проверка |
|---|---------|
| F1 | Название теста описывает поведение, без номеров |
| F2 | Нет `.only` / `.skip` (кроме intentional skip с комментарием) |
| F3 | Нет закомментированного кода |
| F4 | Нет динамических `import()` в тестах — обычные импорты в шапке |
| F5 | `npm run typecheck` — без ошибок |

## Порядок выполнения

### Шаг 0: Пройти по Checklist

Проверить каждый пункт A1–F5. Записать результат:
- Все ✅ → перейти к Шагу 1
- Есть ❌ → зафиксировать нарушения, исправить, перейти к Шагу 1

### Шаг 1: Функциональное ревью
Проверить тест на полноту покрытия:
- Покрыты ли все ожидаемые состояния UI?
- Проверены ли edge cases (пустые состояния, ошибки валидации)?
- Корректно ли тест работает при ретраях (retries: 2)?
- Нет ли хрупких ассертов, которые могут падать из-за таймингов?

### Шаг 2: Ревью по чек-листам

**Использовать 3 чек-листа:**
- `test-reliability.md` — 17 паттернов надёжности (race conditions, fragile selectors, weak assertions, assertion-title mismatch, inline locators, hardcoded values, missing cleanup, test order dependency, missing error messages, stale elements, non-retrying assertions, overly broad scope, missing await on expect, conditional assertions, type coercion, discarded returns, missing data load wait)
- `test-antipatterns.md` — 11 анти-паттернов эффективности (hard waits, double-wait chains, broken Promise.all, unnecessary wrappers, redundant logins, redundant setup/cleanup, missing waitForResponse, missing await on fire-and-forget, asserting on Locator, waits in shared hooks, shared mutable state)
- `test-pom-review.md` — 6 проверок PO (hidden waits, missing await, fragile selectors, error swallowing, isVisible wrappers, complex methods)

**Workflow:**
1. Открыть тестовый файл + используемые PO
2. Пройти по всем трём чек-листам
3. Каждое нарушение → **записать в chat report** (НЕ в код!)

### Шаг 3: Смысловое ревью — соответствие кода заявленному

**Проверяет, что тест реально тестирует то, что заявлено.**

#### 3.1: Title ↔ Assertions match
- Прочитать `test('title', ...)` — что обещает заголовок?
- Пройти по всем `expect(...)` в тесте — проверяют ли они то, что обещает title?
- **Нарушение:** title говорит "generate report", но ассерт только "evaluation in table"
- **Записать в chat report:** `MEDIUM: TC-91911 title "generate report" — no assertion checks report exists`

#### 3.2: TC steps coverage
- Для каждого `@TC-XXXX` в тесте проверить:
  - Все шаги `[step N]` из CSV покрыты кодом?
  - Все ассерты `[step N.x] exp` из CSV проверены?
  - Нет ли "мёртвых" шагов (код есть, но без `expect`)?
- **Записать в chat report:** `HIGH: TC-91874 [step 6] not verified — Edit clicked but result not asserted`

#### 3.3: No false positives
- Тест проходит, но **не проверяет ключевое поведение**
- Пример: `rateCategory(6)` → `toBeHidden()` — проверяет что input исчез, но не проверяет warning message
- **Записать в chat report:** `MEDIUM: Assertion checks redirect but not that evaluation was saved`

#### 3.4: Dead code detection
- Есть ли шаги/ассерты которые ничего не проверяют?
- `await expect(locator).toBeVisible()` — если это не ключевое состояние, а просто "прошёл ли тест?"
- `await evaluationPage.waitForSubmitEnabled()` — без последующего `submitButton.click()` — мёртвый код
- **Записать в chat report:** `LOW: waitForSubmitEnabled() without subsequent submit — dead code`

### Шаг 4: Ревью читаемости и поддерживаемости
- Понятны ли имена переменных и методов PO?
- Не слишком ли длинный тест (> 30 строк)? Если да — рассмотреть выделение методов PO
- Есть ли повторяющийся код, который можно вынести в PO?
- Соответствует ли стиль остальным тестам в проекте?

### Шаг 5: Внесение улучшений
На основе ревью:
- Переименовать непонятные методы/локаторы
- Вынести повторяющуюся логику в методы PO
- Добавить недостающие ассерты
- Улучшить надёжность хрупких проверок
- Исправить любые нарушения AGENTS.md
- **После каждого изменения — запускать тест для проверки**

### Шаг 6: Повторный запуск
```bash
npm run test:owner   # или test:sysadmin / test:coach / test:parent / test:athlete / test:all
```
Убедиться, что все правки не сломали проходящий тест.

### Шаг 7: Финальный отчёт
Представить результат ревью:
```
## Ревью: [Название теста]

### Critical

### High

- Результат запуска: PASS / FAIL
- Статус: "Тесты проходят → переходим к Харвестеру" или "Нужны доработки → повторный запуск"
```

## Правила
- ❄️ ВСЕГДА проводить холодное ревью — только финальный код, никаких историй правок
- ВСЕГДА запускать тесты после правок
- Вносить минимальные улучшения — не переписывать ради переписывания
- Если тест проходит и нет критических проблем → похвалить и перейти дальше
- **ВСЕГДА проверять смысловое соответствие: title → assertions → TC steps**
- **ВСЕ результаты ревью писать в chat report, НЕ в тестовый файл**
- **Финальный тестовый файл должен быть чистым: только код + JSDoc `/** @TC-... */`**
- Если найдены нарушения AGENTS.md → обязательно исправить
- Если тест слишком длинный → предложить рефакторинг с выделением методов PO
- НИКОГДА не менять поведение теста без согласования с пользователем
- Фиксировать все найденные проблемы для анализа в Харвестере
