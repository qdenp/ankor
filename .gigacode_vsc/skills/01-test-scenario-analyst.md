# Скилл: Анализатор Тестовых Сценариев

## Назначение
Анализировать новый тестовый сценарий, проверять наличие дублей в существующих тестах, и составлять детальный план шагов.

## Когда использовать
Когда пользователь описывает новый тестовый сценарий или требование к тестированию.

## Порядок выполнения

### Шаг 1: Анализ требований
- Разобрать описание сценария от пользователя
- Определить: какие роли задействованы, какой функционал тестируется, ожидаемое поведение
- Определить, какому номеру меню/файлу это соответствует (из таблицы в AGENTS.md)

### Шаг 2: Проверка на дубликаты
- Поискать существующие тестовые файлы с похожими сценариями
- Проверить `tests/specs/{role}/` на наличие связанных тестов
- Поискать в page object соответствующие методы
- Использовать grep для поиска существующего покрытия функционала

**Команды поиска дублей в этом проекте:**
```bash
# Поиск по методам PO:
grep -r "createAthlete" tests/specs/
grep -r "createCoach" tests/specs/
grep -r "createParent" tests/specs/
grep -r "createPlan" tests/specs/
grep -r "getAthleteRow\|getCoachRow\|getParentRow\|getPlanRow" tests/specs/

# Список существующих тестов по ролям:
ls tests/specs/owner/
ls tests/specs/coach/
ls tests/specs/parent/
ls tests/specs/athlete/
```

### Шаг 3: Выявление пробелов
- Что НЕ покрыто существующими тестами?
- Есть ли граничные случаи, которые не протестированы?
- Есть ли новый функционал/поток, требующий новых тестов?

### Шаг 4: Составление шагов теста
Создать детальный пошаговый план:
```
## Тестовый сценарий: [Название]

**Роль:** [owner/coach/parent/athlete/sysadmin]
**Файл:** [NN-topic.spec.ts]
**Связанный PO:** [page-object.ts]

### Предварительные условия
- Пользователь авторизован как [роль]
- [Любые необходимые настройки данных]

### Шаги теста
1. Перейти на [страницу/маршрут]
2. [Действие - например, нажать кнопку, заполнить форму]
3. [Действие - например, выбрать опцию из выпадающего списка]
4. [Действие - например, отправить форму]
5. Проверить: [ожидаемое состояние UI]
6. Проверить: [ожидаемое состояние данных]

### Ассерты (web-first, ТОЛЬКО через PO)
- await expect(athletePage.getAthleteRow(email)).toBeVisible({ timeout: TIMEOUTS.long })
- await expect(planPage.getPlanRow(planName)).toBeVisible({ timeout: TIMEOUTS.long })
- await expect(page).toHaveURL(/expected-route/)
- await expect(po.heading).toBeVisible()
- await expect(po.searchInput).toHaveValue(searchTerm)
- await expect(po.athleteRows).toHaveCount(N)

### Требования к данным
- [Любые специфические тестовые данные]
- [Существующие пользователи из 00-create-users.spec.ts, которые можно использовать]
```

### Шаг 5: Предоставление на утверждение
Показать составленный план пользователю и запросить подтверждение или правки.

## Правила
- ВСЕГДА проверять существующие тесты перед составлением новых
- ВСЕГДА следовать соглашениям AGENTS.md (названия тестов, web-first ассерты и т.д.)
- ВСЕГДА использовать web-first ассерты (expect с авто-ретраем)
- НИКОГДА не хардкодить таймауты — использовать TIMEOUTS из config.ts
- НИКОГДА не использовать `page.locator()` / `page.getByRole()` / `page.getByText()` напрямую в тестах — только методы и свойства PO
- Учитывать все роли, которые могут быть затронуты этим функционалом
- Если найден дубликат — сообщить об этом и предложить расширить существующий тест вместо создания нового

## Формат вывода
Всегда представлять анализ в такой структуре:
1. **Текущее покрытие:** [что уже протестировано]
2. **Анализ пробелов:** [чего не хватает]
3. **Предлагаемые шаги теста:** [детальные шаги]
4. **Необходимые изменения:** [новые методы PO, новый тестовый файл или расширение существующего]
5. **Запрос на утверждение:** "Утверждаете ли вы этот план?"
