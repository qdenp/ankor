# test-review-checklist.md — чек-лист ревью (шаг 04)

Один чек-лист для спеков и Page Objects. Правило — одна строка; подробности и образцы — AGENTS.md и реальный код.
Результат ревью — **только отчёт в чат** (severity, `файл:строка`, пункт, что исправить); код на этом шаге не правится.
Одно нарушение — один пункт: выбирать самый конкретный.

Severity: **C** critical — тест может пройти, ничего не проверив, или флакает; **H** high; **M** medium; **L** low.

## A. Ассерт реально проверяет (ложный PASS)
- **A1 C** — `await` перед каждым `expect(...)` с web-first матчером и перед каждым действием PO; промис без `await` не выполняется.
- **A2 C** — ассерт на результат действия, а не на объект: нет `expect(locator).toBeTruthy()`, `expect(promise)…`, `expect(await x.isVisible()).toBe(true)`.
- **A3 C** — нет одноразовых чтений: `expect(await locator.count()).toBe(n)`, `textContent()` → только `toHaveCount` / `toHaveText` (AGENTS §3).
- **A4 C** — ассерт не прячется в `if (await x.isVisible())`, `try/catch` или ветку, которая может не выполниться.
- **A5 H** — проверяется результат, а не видимость контейнера: после деактивации — статус `Inactive` в строке, после удаления — `Segments (0)`, после создания — запись в списке (реальные случаи 2.5, 2.10).
- **A6 H** — отрицательная проверка (`toBeHidden`, `not.toHaveURL`) идёт после положительной на той же странице; иначе проходит до рендера или при пустом списке (2.4: вкладка Invited была пустой).
- **A7 H** — регулярка в `toHaveURL` не совпадает с исходным адресом: `/practice-plans/` совпадала и с `/practice-plans/new` (2.1).
- **A8 M** — название теста = то, что он проверяет («full CRUD», а проверялась видимость кнопок — 2.9); кейс покрыт не полностью → `test.skip` с TODO после `allureId` (AGENTS §6).
- **A9 L** — у неочевидного ассерта есть сообщение вторым аргументом.

## B. Ожидания и гонки
- **B1 C** — после перехода и после create/edit/delete — `waitForLoading()` (в методе PO); чтение списка до загрузки даёт пустую таблицу (AGENTS §3).
- **B2 H** — нет `waitForTimeout` и `sleep` (ловит `npm run lint`); ожидание — условие: `expect(...)`, `locator.waitFor()`.
- **B3 H** — локатор не «перескакивает»: «первая ячейка с `—`» после ввода значения указывает на другую ячейку — брать ячейку по строке/категории (2.6).
- **B4 M** — ожидания не дублируются (`waitFor` + `toBeVisible` на одном элементе) и не сидят в общих хуках, где умножаются на число тестов.
- **B5 H** — элемент может отсутствовать, а не быть выключенным: перед `isDisabled()` / `isEnabled()` проверить наличие — при одной странице результатов пагинации нет совсем, и проверка ждёт до таймаута (`deactivate-test-users.spec.ts`).

## C. Локаторы и Page Objects
- **C1 H** — в спеке нет `page.getByRole/locator/getByText` (ловит lint); всё через PO.
- **C2 H** — строка — только среди строк таблицы, карточка — `article`; нет `.or(getByText(name))` (находит уведомление) (AGENTS §4).
- **C3 H** — список проверен глазами: таблица или карточки (у дриллов карточки — `getRow` по `row` не находил ничего).
- **C4 M** — локатор по роли и доступному имени; CSS/XPath, `.nth()`, глубокие селекторы — только если роли нет.
- **C5 M** — кнопка создания на странице списка с `.first()` (пустое состояние дублирует кнопку); `createButton` и `saveButton` — разные локаторы.
- **C6 H** — метод PO не глушит ошибку и не возвращает `boolean` вместо ожидания: `isXExists()` после поиска без ожидания загрузки скажет «нет» (athlete/coach/parent-page, только в setup).
- **C7 M** — метод PO делает одно действие; длинный метод с ветвлением по числу опций (`scorecard-template-page.ts` → `fillFirstCategory`) — кандидат на разбиение.
- **C8 M** — PO ждёт состояние, но не проверяет бизнес-результат; статические локаторы — в конструкторе.

## D. Данные стенда и порядок
- **D1 C** — запись создаёт только тест создания; остальные берут её из `test-data-store` (AGENTS §9).
- **D2 H** — созданное удаляется, если можно (команды, черновики), в `finally`/`afterEach`; пользователи — деактивируются в `afterAll`; email пользователя — с `+temp-`.
- **D3 H** — тест работает отдельно (`--grep`): зависимость — через хранилище с понятной ошибкой, не через переменную `describe`, присвоенную другим тестом.
- **D4 H** — тесты разных ролей не меняют одну запись; правка имени возвращается к константе (`ORGANIZATIONS`), не к прочитанному значению.
- **D5 C** — нет новых Submit оценки и других неудаляемых действий без согласия пользователя; группа с ними — `retries: 0`.
- **D6 M** — уникальные имена (`Date.now()`); жёстко заданные email/имена/числа — в `config.ts`.

## E. Структура
- **E1 M** — один логин на тест (`loginAs`), без повторного входа той же ролью; вход другого пользователя — в отдельном контексте.
- **E2 M** — первая строка теста — `allure.allureId('<test_case_id>')`; один тест — один кейс.
- **E3 L** — тест не проверяет несвязанные функции разом; длинный flow — по шагам кейса.
